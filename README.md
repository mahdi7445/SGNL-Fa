# راهنمای راه‌اندازی ربات Tradeiscool (نسخه یکپارچه ۵.۳)

## 🆕🆕 بازبینی جامع: رفعِ قطعیِ «قطعی بعد از ۵ ساعت و ۲۰ دقیقه» + «پیام‌های سیگنال بسته‌شده دوباره ارسال می‌شود»
طبق درخواست صریح کاربر، همه‌ی سناریوهای ممکن بررسی و سه رفعِ ریشه‌ای زیر اعمال شد:

1. **قطعیِ ادامه‌ی خودکار بعد از ~۵ ساعت و ۲۰ دقیقه (رفع نهایی):** تا اینجا تنها
   تضمینِ ادامه‌ی خودکار، cron هر ۱۰ دقیقه + صف‌شدنِ concurrency بود - که به
   قابلیت‌اطمینانِ زمان‌بندی خودِ GitHub متکی بود (چیزی که خودِ گیت‌هاب هم
   تضمینش نمی‌کند: «the schedule event can be delayed during periods of high
   loads»). حالا آخرین مرحله‌ی `signals.yml` (`Trigger next run immediately`)
   دیگر منتظر تیک بعدیِ cron نمی‌ماند - همین که این اجرا (هر طور، طبیعی یا با
   خطا) تمام می‌شود، خودش مستقیماً از طریق GitHub API یک اجرای جدید تریگر
   می‌کند؛ شکاف احتمالی از «تا ۱۰ دقیقه» به «چند ثانیه» رسید. cron هر ۱۰ دقیقه
   به‌عنوان لایه‌ی دوم پشتیبان (برای وقتی خودِ این فراخوانی API شکست بخورد)
   نگه داشته شد.
   ⚠️ **شرط حیاتی که هیچ کدی نمی‌تواند جایگزینش شود:** طبق هشدار قبلیِ همین
   فایل، **ریپازیتوری باید Public باشد**. اگر همچنان Private است، سهمیه‌ی
   رایگان ۲۰۰۰ دقیقه/ماه GitHub Actions (که هر اجرای ۵ ساعت و ۲۰ دقیقه‌ای تقریباً
   ۳۲۰ دقیقه از آن مصرف می‌کند) در کمتر از دو روز تمام می‌شود و بعد از آن
   GitHub خودش از صف‌کردن/شروع هر اجرای جدیدی (چه با cron، چه با این تریگر
   جدید) امتناع می‌کند - این یک محدودیت صورتحساب/پلن گیت‌هاب است، نه چیزی که
   با تغییر کد در bot.py یا signals.yml قابل دور زدن باشد. قبل از هر چیز چک
   کنید: Settings → General → Danger Zone → visibility باید **Public** باشد.
2. **پیام‌های سیگنال‌های قدیمی/بسته‌شده دوباره ارسال می‌شدند (رفع ریشه‌ای):**
   علت واقعی پیدا شد - وضعیت هر معامله (تارگت خورد/استاپ خورد/بسته شد) فقط در
   حافظه فوری بود، ولی ذخیره‌ی دائمی (state.json + git push، تنها منبعی که یک
   اجرای تازه بعد از crash/timeout از رویش می‌خواند) فقط دوره‌ای (هر ۲ دقیقه)
   بود. اگر پروسه دقیقاً در همین فاصله متوقف می‌شد، آن پرچم هرگز به ریموت
   نمی‌رسید و اجرای بعدی، با کندل‌های تاریخیِ بدون‌تغییر، دوباره به همان
   تارگت/استاپِ از قبل رخ‌داده می‌رسید و دوباره پیامش را می‌فرستاد. حالا همین
   که یک پیام واقعاً به تلگرام تحویل داده شد (ورود جدید، هر تارگت، استاپ،
   بسته‌شدن اجباری - هر مسیر: کندلی، WebSocket زنده، REST زنده، ۱ دقیقه‌ای
   ارزهای همسو با روند)، بلافاصله همان‌جا state ذخیره و پوش می‌شود - نه اینکه
   تا ذخیره‌ی دوره‌ای بعدی صبر کند. چون این فقط به ازای پیام‌های واقعاً
   ارسال‌شده اتفاق می‌افتد (نه هر چند ثانیه)، هیچ فشار اضافه‌ای روی حلقه‌ی
   اصلی یا سهمیه‌ی API نمی‌گذارد.
3. **گزارش روزانه‌ی فقط یک‌بار در روز:** بازبینی کامل نشان داد این مورد از قبل
   با یک الگوی چندلایه («pull → mark → push → send» + بازیابی پرچم‌ها از دیسک
   در برابر revert) درست پیاده‌سازی شده بود - چیزی برای تغییر پیدا نشد؛ فقط
   تأیید و مستند شد.

هیچ‌کدام از این تغییرات روی منطق تشخیص سیگنال، حد ضرر، تارگت‌ها، تریلینگ، یا
فرمت پیام‌ها اثر نگذاشتند - فقط ذخیره‌سازی/زمان‌بندی سطح پایین‌تر شد.

## 🆕 گروه جدید: «ارزهای همسو با روند بازار» (جایگزین «ارزهای پرتحرک») + تایم‌فریم ۱ دقیقه‌ای رایگان از WebSocket
طبق درخواست کاربر، گروه سوم سیگنال‌دهی («ارزهای پرتحرک» - ثابت ۳ برنده + ۳ بازنده)
با یک منطق جدید و هوشمندتر جایگزین شد:

1. **تشخیص جهت کلی بازار.** `get_market_regime` از روی درصد تغییر ۲۴ساعته‌ی خودِ
   BTC (بدون هیچ درخواست API اضافه) تشخیص می‌دهد بازار صعودی، نزولی یا خنثی است
   (بازه‌ی خنثی: `MARKET_REGIME_NEUTRAL_BAND_PCT`، پیش‌فرض ±۰.۵٪).
2. **انتخاب یک‌طرفه.** اگر بازار صعودی → `TREND_ALTS_COUNT` (پیش‌فرض ۳) آلت‌کوینی
   که بیشترین صعود را نسبت به BTC داشته‌اند انتخاب می‌شوند؛ اگر نزولی → بیشترین
   نزول نسبت به BTC. اگر خنثی، آن روز هیچ ارزی انتخاب نمی‌شود. لیست فقط **یک‌بار
   در روز** (`TREND_ALTS_REFRESH_HOUR`، پیش‌فرض ۰۰:۰۰ UTC) تازه می‌شود.
3. **تایم‌فریم ۱ دقیقه‌ای رایگان و لحظه‌ای.** رصد REST تایم‌فریم ۱ دقیقه‌ای برای
   چند نماد از کل سقف رایگان Twelve Data (۸۰۰ درخواست/روز) به‌تنهایی عبور می‌کند
   (محاسبه‌ی کامل در کامنت بالای `TIMEFRAMES`/`TREND_ALTS_*` در `bot.py`). به‌جایش
   کندل ۱ دقیقه‌ای از همان تیک‌های زنده‌ی WebSocket که این ارزها را برای رصد
   معاملات باز هم پوشش می‌دهد، در حافظه ساخته می‌شود (`feed_1m_candle_tick` /
   `get_closed_1m_candles`) - هزینه‌ی API صفر، و چون هر چند ثانیه (نه هر ۵ دقیقه)
   چک می‌شود، سیگنال ۱ دقیقه‌ای عملاً چند ثانیه بعد از بسته‌شدن واقعیِ کندل کشف و
   در کانال فرستاده می‌شود.
4. **تایم‌فریم‌های ۵د/۱۵د/۱ساعته** همچنان از Twelve Data REST می‌آیند، با فرکانسی
   که دقیقاً هم‌اندازه‌ی سهمیه‌ی قبلیِ «ارزهای پرتحرک» (~۶۶ درخواست/روز) نگه داشته
   شده - سهمیه‌ی کل سیستم تغییر نکرده، فقط تعداد ارز نصف و فرکانس هر کدام تقریباً
   دو برابر شد.
5. **رصد لحظه‌ای معاملات باز روی هر ۴ تایم‌فریم** (نه فقط ۱د) - چون این ارزها به
   همان استریم WebSocket واحد وصل‌اند، `check_ws_open_trades` حالا معاملات باز
   این گروه را هم (نه فقط واچ‌لیست اصلی) با آخرین تیک زنده چک می‌کند.

## 🆕 بازبینی برنامه‌نویس: اصلاح سهمیه‌ی API + رصد زنده‌ی ۳۰ ارز برتر/ارزهای پرتحرک + پایداری بیشتر
یک برنامه‌نویس دیگر کد را بررسی و چند پیشنهاد داد. تحلیل کامل و نتیجه:

**اعمال‌شده (بهبود واقعی، بدون تغییر منفی):**
- **اصلاح یک باگ واقعی در محاسبه‌ی سهمیه:** نسخه‌ی قبلی فرض کرده بود «۴ نماد ×
  ۵ تایم‌فریم، هرکدام هر ۵ دقیقه چک می‌شوند» زیر سقف ۸۰۰ درخواست/روز Twelve Data
  می‌ماند - این محاسبه ناقص بود (فقط برای ۱ نماد درست بود، ضرب در ۴ نماد از سقف
  عبور می‌کرد). راه‌حل: واچ‌لیست اصلی به ۲ نماد با بیشترین نقدشوندگی (`SOL`, `XRP`)
  محدود شد و فرکانس تایم‌فریم‌های ۱د/۵د با افزایش تعداد کندلِ هر درخواست (که رایگان
  است) کاهش یافت - محاسبه‌ی کامل در کامنت بالای `WATCHLIST_SYMBOLS` در `bot.py`.
- **رصد زنده‌ی REST برای ۳۰ ارز برتر/ارزهای پرتحرک:** این دو گروه قبلاً هیچ رصدی
  بین دو اسکن کندلی نداشتند. تابع آماده‌ی `fetch_live_price` (قبلاً فقط برای طلا
  نوشته شده و بلااستفاده مانده بود) دوباره فعال شد تا معاملات باز این دو گروه هم
  هر ۳۰ دقیقه با قیمت لحظه‌ای چک شوند.
- **ذخیره‌سازی اتمیک state.json** (فایل موقت + `os.replace`).
- **بازگشت به آخرین state سالم** اگر یک دور اسکن با خطای پیش‌بینی‌نشده متوقف شود.
- **محافظ بحرانی دور حلقه‌ی اصلی** تا حتی در خطای کاملاً غیرمنتظره هم آخرین state
  ذخیره و پوش شود.
- **حذف چاپ طول کلیدهای API از لاگ** (هم در `bot.py` هم در `signals.yml`).
- کاهش dpi چارت از ۱۵۰ به ۱۰۰ (سرعت رندر بیشتر، افت کیفیت ناچیز).

**رد‌شده (چون منطق/عملکرد را خراب می‌کرد یا خواسته‌ی صریح کاربر را نقض می‌کرد):**
- «تعداد کندل هر درخواست از ۱۰ به ۵ کم شود» - رد شد: هزینه‌ی هر درخواست در
  Twelve Data صرف‌نظر از تعداد کندل ثابت است، پس این تغییر هیچ سهمیه‌ای صرفه‌جویی
  نمی‌کرد و فقط ریسک از‌قلم‌افتادن کندل را بالا می‌برد.
- «تایم‌فریم ۱د/۵د فقط هر ۱۵ دقیقه کندل تازه بگیرند» و «۳۰ ارز برتر به ۴ساعته
  برگردد» - رد شد: مستقیماً با خواسته‌ی صریح قبلی کاربر («فقط تایم‌فریم زیر ۴ ساعت،
  نهایت سرعت/دقت») در تضاد بود.
- «چارت فقط برای ورود، نه خروج» - از قبل همین‌طور پیاده‌سازی شده بود؛ نیازی به
  تغییر نبود.
- «threading.Lock برای state» - بررسی شد و مشخص شد در طراحی فعلی (state فقط در
  یک ترد خوانده/نوشته می‌شود) هیچ Race Condition واقعی‌ای وجود ندارد که این قفل
  رفع کند؛ عمداً اضافه نشد تا پیچیدگی بی‌فایده به کد اضافه نشود.
- ماژولار‌کردن به چند فایل، تست‌های واحد، گزارش‌دهی پیشرفته (Profit Factor و...)،
  چند-کاناله‌کردن، رمزنگاری state.json - همگی معقول ولی خارج از دامنه‌ی این بازبینی
  (تغییرات ساختاری بزرگ یا قابلیت‌های جدید، نه رفع مشکل)؛ برای درخواست جداگانه.

## 🆕 بروزرسانی بزرگ: کانال اختصاصی آلت‌کوین + فقط تایم‌فریم زیر ۴ ساعت + فرمت پیام دقیقاً مطابق تصویر مرجع
طبق درخواست صریح کاربر، سه تغییر بنیادی روی `bot.py` اعمال شد:

1. **بیت‌کوین و اتریوم کامل حذف شدند.** این کانال از این به بعد فقط برای
   آلت‌کوین‌های بازار کریپتوکارنسی است - هم از واچ‌لیست اصلی، هم از ۳۰ ارز برتر،
   هم از ارزهای پرتحرک. واچ‌لیست اصلی: `SOL`, `XRP` (بدون
   محدودیت تایم‌فریم + استریم زنده‌ی WebSocket که قبلاً مخصوص BTC/ETH بود).
   تنها جایی که هنوز BTC دیده می‌شود «عملکرد نسبی به BTC» است - صرفاً یک معیار
   مقایسه‌ای برای انتخاب کاندیدهای «ارز پرتحرک»، نه یک سیگنال معاملاتی برای BTC.

2. **همه‌ی تایم‌فریم‌ها به زیر ۴ ساعت محدود شدند.** تایم‌فریم‌های ۴ساعته و هفتگی
   که قبلاً وجود داشتند کامل حذف شدند. تایم‌فریم‌های فعال الان: `1m`, `5m`,
   `15m`, `30m`, `1h`. هر تایم‌فریم با فرکانسی متناسب با هزینه‌ی واقعی‌اش در سهمیه‌ی
   روزانه‌ی Twelve Data (۸۰۰ درخواست/روز در پلن رایگان) چک می‌شود - جزئیات کامل در
   کامنت بالای `WATCHLIST_SYMBOLS` در `bot.py` - و معاملات باز واچ‌لیست اصلی هر ۵
   ثانیه با قیمت زنده‌ی WebSocket رصد می‌شوند (سرعت/دقت بیشتر از هر نسخه‌ی قبلی).

3. **فرمت پیام‌ها دقیقاً مطابق تصویر نمونه‌ی ارسالی بازنویسی شد**، از جمله:
   - پیام ورود حالا هر ۴ تارگت را با قیمت دقیقشان نشان می‌دهد (نه فقط Entry/Stop).
   - پیام برخورد به تارگت: `✅ Target N HIT (rR) — SYMBOL TF` + خط قیچی
     (`✂️ Close X% ...`) + `📊 Result so far: +2.10R (profit)`.
   - هیچ سیگنالی بدون توضیح نحوه‌ی بسته‌شدنش (تارگت/استاپ/ریسک‌فری/رانر) نمی‌ماند -
     هر پیام خروج دقیقاً می‌گوید چند درصد پوزیشن با چه علتی بسته شده.



## ⚠️⚠️ حتماً قبل از فعال‌کردن بخوان: این ریپو باید Public باشد
راهنمای قبلی همین فایل صراحتاً گفته بود ریپازیتوری را **Private** بسازید. آن
توصیه برای مدل قدیمی (هر اجرا ~۱۰ ثانیه) درست بود، ولی با تبدیل به پروسه‌ی پیوسته
(پایین‌تر توضیح داده شده) **دیگر درست نیست**: هر اجرا ~۵ ساعت و ۲۰ دقیقه طول
می‌کشد و هر ۵ ساعت دوباره تریگر می‌شود. اگر این ریپو Private بماند، سهمیه‌ی رایگان
۲۰۰۰ دقیقه/ماه GitHub Actions در **کمتر از دو روز** تمام می‌شود و بعد از آن همه‌ی
اجراها متوقف می‌شوند (دقیقاً همان نکته‌ای که خودت در کامنت subscription_bot.yml
نوشته بودی). ریپازیتوری را از Settings → General → Danger Zone → Change visibility
به **Public** تغییر بده (state.json و کدها هیچ کلید/رمزی داخلشان نیست، Secrets
جدا و امن می‌مانند)، دقیقاً مثل ریپوی `candle_engine.py`.

## 🆕 بروزرسانی بزرگ: تبدیل به پروسه‌ی پیوسته (رفع تاخیر سیگنال‌های تایم‌فریم پایین)
تا اینجا `bot.py` یک اسکریپت GitHub Actions بود که هر ۱۵ دقیقه اجرا و خارج می‌شد.
مشکل بنیادی این مدل: (۱) GitHub Actions زمان دقیق اجرای scheduled workflow را
تضمین نمی‌کند (می‌تواند چند دقیقه دیر شروع شود)، و (۲) بین دو اجرا هیچ رهگیری‌ای
از قیمت وجود نداشت. برای سیگنال‌های تایم‌فریم ۱۵ دقیقه‌ای این تاخیر می‌توانست
سیگنال را عملاً بلااستفاده کند.

**راه‌حل واقعی** (نه تنظیم دوباره‌ی زمان‌بندی، بلکه تغییر معماری): `bot.py` حالا
دقیقاً مثل `candle_engine.py` به یک پروسه‌ی پیوسته تبدیل شده که تا ~۵ ساعت و ۲۰
دقیقه در هر اجرای GitHub Actions زنده می‌ماند:

- **اتصال WebSocket زنده به Coinbase برای بیت‌کوین/اتریوم** - دقت زیر ۱۰ ثانیه،
  بدون هیچ هزینه‌ی API (برخلاف Twelve Data که سهمیه‌ی روزانه دارد). معاملات باز
  این دو نماد هر ۵ ثانیه با آخرین تیک قیمت چک می‌شوند.
- **طلا (XAU)** چون هیچ WebSocket رایگانی ندارد، هر ۱۵ دقیقه با یک درخواست REST
  سبک (`/price`، نه کندل کامل) رهگیری می‌شود - بین دو کندل هم اگر تارگت/استاپ
  بخورد، همان لحظه تشخیص داده می‌شود.
  - **۳۰ ارز برتر و ارزهای پرتحرک** با همان سیستم کندلی قبلی (هر ۵ دقیقه یک دور
  اسکن کامل) پوشش داده می‌شوند - این‌ها نیازی به دقت زیر-دقیقه ندارند.
- **کامیت خودکار state.json هر ۲ دقیقه** (نه فقط در پایان اجرا) - اگر پروسه هر
  جایی متوقف شود، پیشرفت از دست نمی‌رود.
- منطق تشخیص سیگنال، حد ضرر، ۴ تارگت، تریلینگ، رانر، چارت، و فرمت پیام‌ها **هیچ
  تغییری نکرده** - فقط نحوه‌ی اجرا (پیوسته به‌جای دوره‌ای) عوض شده.

**نتیجه‌ی هر سیگنال همیشه مشخص می‌شود:** هر معامله‌ی باز از حداقل دو مسیر مستقل
رصد می‌شود (کندل تازه‌بسته‌شده + قیمت لحظه‌ای)، و هر بسته‌شدن (تارگت/استاپ/
ریسک‌فری/تریلینگ/رانر/سیگنال مخالف) هم در پیام کانال (خط `Result: ...R`) و هم در
گزارش روزانه‌ی عملکرد ثبت می‌شود - هیچ معامله‌ای بی‌نتیجه نمی‌ماند.

**نیازمندی جدید:** `websocket-client` (به requirements.txt اضافه شد).

## ⚠️ درباره‌ی «فوروارد پیام برای تبدیل» - هنوز پیاده نشده
یک درخواست دیگر هم بود: پیامی که از کانال «TRADE'S COOL (VIP)» به ربات فوروارد
می‌شود، خودکار به همین فرمت تبدیل و ارسال شود. **این با معماری فعلی `bot.py`
ممکن نیست** - چون `bot.py` یک اسکریپت GitHub Actions است که هر ۱۵ دقیقه اجرا و
خارج می‌شود (مثل قبل هم مستند بود)، نمی‌تواند منتظر پیام فورواردی از کاربر بماند؛
این نیاز به یک فرآیند همیشه-روشن (شبیه `subscription_bot.py`) دارد که پیام‌های
ورودی را بشنود.

از طرفی، چون فرمت خروجی خودِ `bot.py` از این به بعد دقیقاً همین شکل رفرنس است،
احتمالاً دیگر نیازی به فوروارد دستی برای تبدیل نیست - سیگنال‌های جدید همین الان
با همین فرمت مستقیم در کانال ارسال می‌شوند. اگر هنوز قابلیت جداگانه‌ی «فوروارد و
تبدیل» (مثلاً برای پیام‌های قدیمی یا از منبع دیگر) لازم است، باید جداگانه صحبت
کنیم که آیا یک اسکریپت همیشه-روشن جدید (با هزینه‌ی دقیقه‌ی Actions اگر ریپو
Private باشد) ارزشش را دارد یا نه.

## 🆕 بروزرسانی: تارگت + عکس چارت برای همه‌ی سیگنال‌های کندلی (مثل candle_engine.py)
هر سیگنال کندلی (واچ‌لیست اصلی، ۳۰ ارز برتر، ارزهای پرتحرک) از این به بعد یک
معامله‌ی کامل با مدیریت پوزیشن است، دقیقاً مثل ربات `candle_engine.py`:

- **حد ضرر:** ترکیب EMA7 و آخرین سوینگ لو/های (۱۰ کندل قبل) + بافر ۰.۷۵×ATR
- **۴ تارگت (R:R):** تارگت۱=1R، تارگت۲=2R (+ انتقال استاپ به نقطه‌ی ورود)، تارگت۳=3R
  (+ شروع تریلینگ‌استاپ)، تارگت۴=4R (+ ۱۵٪ باقی‌مانده به‌عنوان «رانر» با تریلینگ باز می‌ماند)

  هر پیام خروج (تارگت/استاپ/ریسک‌فری/تریلینگ/رانر/بسته‌شدن اجباری)
- پیام‌های خروج روی پیام سیگنال ورود **ریپلای** می‌زنند (thread)
- اگر سیگنال مخالف بیاید در حالی که معامله‌ی قبلی هنوز باز است، اول معامله‌ی قبلی با
  قیمت بازار بسته می‌شود (پیام جداگانه) و بعد سیگنال جدید باز می‌شود - هیچ‌وقت هج نمی‌شود

**نکته‌ی مهم درباره‌ی سهمیه‌ی API:** برخلاف candle_engine.py که پیوسته اجرا می‌شود و
می‌تواند بین دو کندل هم با قیمت زنده (WebSocket/REST) وضعیت معامله را چک کند،
bot.py هر ۱۵ دقیقه یک‌بار اجرا می‌شود؛ چک کردن معامله‌ی باز هم از همان کندل‌هایی
انجام می‌شود که برای تشخیص سیگنال جدید هم‌اکنون دریافت شده‌اند (هزینه‌ی اضافه‌ی
API ندارد)، فقط ممکن است کشف خروج تا بسته‌شدن کندل بعدی (نه لحظه‌به‌لحظه) طول بکشد.

سیگنال‌های جریان استیبل‌کوین (FLOW) عمداً بدون تارگت/چارت باقی ماندند، چون بر پایه‌ی
جریان ورودی/خروجی صرافی هستند نه پرایس‌اکشن کندلی، و SL/تارگت طبیعی ندارند؛ ظاهر
پیامشان (خط اول، امضا، فوتر) هنوز با بقیه‌ی سیگنال‌ها یکسان است.

نیاز جدید: `pandas`، `matplotlib`، `mplfinance` (در requirements.txt اضافه شدند).

نمی‌شود. GitHub Actions هم رایگان است و نیازی به هاست ندارید.

## مراحل راه‌اندازی (یک‌بار انجام می‌شود)

### ۱. ساخت ریپازیتوری
یک ریپازیتوری **خصوصی (Private)** در GitHub بسازید و همه‌ی فایل‌های این پوشه
(`bot.py`, `requirements.txt`, `state.json`, پوشه‌ی `.github`) را در آن آپلود کنید.
(از طریق وب گیت‌هاب: Add file → Upload files)

### ۲. تعریف Secrets
در ریپازیتوری: **Settings → Secrets and variables → Actions → New repository secret**
این ۴ مورد را اضافه کنید (دقیقاً با همین اسم):

- `TELEGRAM_BOT_TOKEN` — توکن رباتی که از BotFather گرفته‌اید
- `TELEGRAM_CHANNEL_ID` — آیدی عددی کانال/چتی که پیام‌ها باید به آن برود
- `COINMARKETCAP_API_KEY` — کلید رایگان از coinmarketcap.com/api
- `LIVECOINWATCH_API_KEY` — کلید رایگان از livecoinwatch.com/tools/api

> اگر فعلاً فقط سیگنال کندلی برایتان مهم است و نمی‌خواهید الان کلید CMC/LiveCoinWatch
> بسازید، مشکلی نیست — ربات به‌طور خودکار فقط اسکن جریان/عملکرد را رد می‌کند و
> سیگنال کندلی طبق برنامه ادامه پیدا می‌کند. کافیست `TELEGRAM_BOT_TOKEN` و
> `TELEGRAM_CHANNEL_ID` تنظیم شده باشند.

### ۳. فعال‌سازی Actions
به تب **Actions** بروید و اگر پیام تایید ظاهر شد، گزینه‌ی فعال‌سازی ورک‌فلوها را بزنید.

### ۴. تست دستی
در تب Actions، روی ورک‌فلوی **Tradeiscool Signals** کلیک کنید → **Run workflow** →
گزینه‌ی `force_run_all` را `true` بگذارید → Run workflow.
این باعث می‌شود ربات صرف‌نظر از ساعت فعلی، همه‌ی اسکن‌ها را همین الان انجام دهد تا
مطمئن شوید پیام به تلگرام می‌رسد.

## نکات مهم

- **اجرای اولیه‌ی سیگنال کندلی** روی صدها نماد Binance انجام می‌شود و ممکن است چند
  دقیقه طول بکشد و در همان اجرای اول، اگر چند ارز هم‌زمان شرایط سیگنال را داشته باشند
  چند پیام پشت‌سرهم دریافت کنید — این طبیعی است و فقط مخصوص اجرای اول است.
- **فایل `state.json`**: ربات بعد از هر اجرا این فایل را خودش در ریپازیتوری کامیت
  می‌کند (برای جلوگیری از سیگنال تکراری). لازم نیست کاری با آن انجام دهید. همین
  کامیت‌های خودکار همچنین باعث می‌شود گیت‌هاب ورک‌فلوی زمان‌بندی‌شده را به‌خاطر
  «عدم فعالیت ریپو» غیرفعال نکند.
- **قابلیت چت با ربات (فرستادن اسم ارز و گرفتن گزارش)** در این نسخه وجود ندارد، چون
  نیاز به یک فرآیند همیشه-روشن دارد که با مدل GitHub Actions (اجرا-و-خروج) سازگار نیست.
- **درباره‌ی سیگنال جریان استیبل‌کوین**: این بخش برای دریافت داده از یک سایت
  (cryptometer.io) حدس می‌زند و می‌تواند شکننده باشد؛ اگر داده‌ی واقعی در دسترس
  نباشد، آن دور اسکن به‌سادگی رد می‌شود (بدون ارسال داده‌ی ساختگی).
- زمان‌بندی‌ها بر اساس **ساعت UTC** است، نه ساعت تهران (تهران = UTC + ۳:۳۰).

## تغییر لیست ارزهای اسکن کندلی
واچ‌لیست اصلی (نمادهایی که همه‌ی تایم‌فریم‌ها + استریم زنده‌ی WebSocket را دارند)
با دیکشنری `WATCHLIST_SYMBOLS` در `bot.py` کنترل می‌شود (الان: `SOL`, `XRP`,
`ADA`, `DOGE`). برای اضافه/حذف نماد، همین دیکشنری را ویرایش کنید - اگر نماد
جدید نیاز به استریم زنده هم دارد، حتماً روی Coinbase (`WS_SYMBOL_MAP` به‌صورت
خودکار از همین دیکشنری ساخته می‌شود) هم موجود باشد.

نمادهای «۳۰ ارز برتر» و «ارزهای همسو با روند بازار» به‌صورت پویا و خودکار از
CoinMarketCap انتخاب می‌شوند (`TOP30_COUNT` و `TREND_ALTS_COUNT` تعداد آن‌ها را
کنترل می‌کنند؛ `MARKET_REGIME_NEUTRAL_BAND_PCT` و `TREND_ALTS_REFRESH_HOUR` هم
جهت‌گیری بازار و ساعت بروزرسانی روزانه را کنترل می‌کنند) - نیازی به دستکاری
دستی برای این دو گروه نیست.
